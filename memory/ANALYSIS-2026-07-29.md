## Короткий вердикт
**Мышление — на профессиональном уровне, реализация — нет (пока).** Архитектура и продумка
(двойная запись, неизменяемый реестр, RLS, шина событий, движок прав) сильнее, чем у

из-за которого развёрнутое приложение, скорее всего, вообще не может связаться с сервером, и
**модель безопасности**, которую нельзя пускать к реальным деньгам без доработки.

## 🔴 Критично (ломает работу или опасно)

### 1. Backend по HTTP → mixed content, приложение не достучится до сервера
`app/js/config.js`: `SUPABASE_URL = 'http://201.51.6.170:8000'` — **обычный HTTP по IP**.
Сайт на GitHub Pages отдаётся только по HTTPS. Браузер **блокирует** запросы с HTTPS-страницы
на HTTP-адрес (mixed content) → в проде приложение не свяжется с базой. Плюс по HTTP пароли,
токены и финансовые данные идут **открытым текстом** — их видно в сети.
**Чинить:** поднять backend за HTTPS (домен + TLS/обратный прокси), в конфиге `https://`.

### 2. Service Worker не узнаёт настоящий backend
`app/sw.js`: `isApiCall` ловит только `supabase.co` / `googleapis.com`. Реальный сервер —
`201.51.6.170`, он под условие не попадает → ответы API кэшируются как файлы приложения
(cache-first). Итог: **устаревшие финансовые данные** из кэша и сломанная офлайн-логика.
**Чинить:** сверять с реальным хостом backend.

## 🟠 Высокий приоритет

### 3. Офлайн работает не так, как обещано в документах
`docs/05-ARCHITECTURE.md` обещает офлайн-просмотр последних загруженных данных
(stale-while-revalidate). По факту SW на API отдаёт `{error:'Offline'}` 503 и ничего не
кэширует → офлайн пользователь видит **ошибки, а не данные**. Либо реализовать кэш чтения,
либо привести обещание в соответствие.

### 4. PIN — это UX-замок, а не защита (а подаётся как безопасность)
`auth.js`: PIN хэшируется `SHA-256('auron:v1:' + pin)` и лежит в `localStorage`. Проблемы:
- 4 цифры = 10 000 вариантов, префикс постоянный (не соль) → хэш подбирается мгновенно;
- лимит «5 попыток → блок» держится **только в localStorage** и обходится их правкой.
Честно: это удобный локальный замок, не защита. Реальная защита — серверный JWT + RLS. Не
позиционировать PIN как «безопасность».

### 5. Токены в localStorage + 18 мест `innerHTML` = поверхность для XSS→кражи токенов
`access_token`/`refresh_token` в `localStorage`, и в коде 18 присваиваний `innerHTML`. Если
хоть одно вставляет неэкранированные данные из базы/пользователя — это XSS, а через него
кража токенов и захват аккаунта. Для приложения о деньгах критично.
**Чинить:** для данных — `textContent`/экранирование, `innerHTML` только с доверенным HTML.

## 🟡 Средний приоритет

### 6. Два HTML-файла — источник рассинхрона
`index.html` (1721 стр.) и `app_bundle.html` (2857 стр.) — оба несут конфиг с секретом и
будут расходиться. Нужен один источник истины; если bundle генерируется — не коммитить или
явно помечать «сгенерировано».

### 7. Нет тестов, линтера и проверок в CI
Только деплой. Для финансового приложения нужен хотя бы smoke-тест ключевых сценариев и
линтер; в `deploy.yml` нет ворот качества (собирается и публикуется без проверок).

### 8. Доступность (a11y)
`viewport: user-scalable=no, maximum-scale=1` **запрещает зум** — нарушение WCAG, особенно
для приложения, которым пользуются с телефона. Проверить также фокус-состояния, контраст,
aria для PIN-клавиатуры и навигации.

### 9. Имена дизайн-токенов в коде расходятся с документом
Значения совпадают, но имена нет: код — `--bg/--ink/--pos/--neg/--warn`, документ —
`--bg-primary/--text-primary/--income/--expense/--transfer`. Привести к одному (документ —
источник истины).

## 🟢 Мелочи / полировка
- `theme-color` рассинхрон: `index.html` `#000000` vs `manifest.json` `#5E5CE6`.
- Логирования/наблюдаемости почти нет (1 console на весь код) — стоит завести захват
  клиентских ошибок (данные покрывают `audit_log`/`analytics_events`, но ошибок фронта — нет).
- Нет `README` для людей (быстрый старт, как устроено).
- `anon`-ключ в репозитории допустим по дизайну Supabase — **только если RLS включён на всех
  таблицах**. Это нужно проверить прицельно, а не считать по умолчанию.

- **История коммитов** показывает живую осмысленную работу: обработка ошибок, адаптив,
  фиксы багов.

## Моё мнение и идеи (то, что вы просили прямо)
Порядок действий, если бы решал я:
1. **HTTPS для backend** — без этого всё остальное не имеет смысла (прод не работает).
2. **Починить хост backend в SW** — чтобы данные не были устаревшими.
3. **Закрыть XSS/токены** — экранирование, аудит `innerHTML`.
4. **Честно про PIN** — оставить как удобный замок, защиту строить на сервере (RLS-аудит).
5. **Ворота качества** — линтер + smoke-тест перед деплоем.

Пожелания на будущее: индикатор «связь с сервером» (учитывая п.1–2), staging-окружение,
простой захват клиентских ошибок в таблицу, один источник истины для HTML.

**Вывод одним предложением:** у вас профессиональный «скелет», которому мешают несколько
конкретных, чинибельных проблем реализации — начать надо с HTTPS и связи с сервером, иначе
всё остальное строится на неработающем фундаменте.
