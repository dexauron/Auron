# Разработка каталога (Way Market · Каталог)

Каталог — **отдельное приложение** внутри репозитория Auron. Свои данные, свои
ветки, свой деплой. С кодом и базой основного приложения Auron (`app/`) НЕ
смешивать. Владелец — не программист; общение и все тексты в интерфейсе — на
русском, простым языком.

## Что это за приложение

- **Одностраничное приложение (SPA) на ванильном JS**, без фреймворков и без
  сборщика. Логика — модули в `catalog/js/modules/` (см. «Устройство кода»).
  Разметка — `catalog/index.html`, стили — `catalog/styles.css`.
- **Сервера нет (с 2026-08-13).** Данные лежат файлами в репозитории:
  - открытая витрина — `catalog/data/{products,groups,popular}.json` (в неё
    попадает только то, что не жалко показать без входа);
  - закрытая часть — ОДИН каталог: опись `catalog.enc` + куски `data/sec/…`,
    зашифрованные случайным «ключом каталога» (AES-GCM, перед шифрованием gzip);
    сам ключ лежит в `keys.json` в маленьких «конвертиках» — по одному на
    каждый пароль (PBKDF2). Читается с raw.githubusercontent.
  - Запись — через GitHub API обычным токеном (PAT), который лежит **только** в
    памяти устройства владельца (`localStorage`, ключ `wm_gh_token`). Токен
    НИКОГДА не коммитить и не выводить в чат.
  - `catalog/js/config.js` — **единственный файл, отличающий один магазин от
    другого**: имя, подпись, логотип, цвет, набор разделов (`CATEGORIES:
    'grocery' | 'none'`), включённые возможности (`FEATURES`) и адрес
    репозитория. Никаких ключей. Названия «Way Market» в модулях быть не должно
    — это проверяет тест `store-config`. Инструкция для чужого магазина —
    `catalog/КАК-СДЕЛАТЬ-СВОЙ-КАТАЛОГ.md`.
- **PWA**: `catalog/sw.js`. Кэш фронта — `wm-catalog-vNN`, фото — `wm-photos-v1`
  (вечный, не чистится).
- **Права** определяются паролем, который ввели на устройстве: пароль владельца
  открывает всё (закупки, продажи, публикация), пароль сотрудника — рабочую
  часть без денег, без пароля — только коды и названия.

## ⚠️ Приватность — главное правило данных

⚠️ **У каталога с августа 2026 ДВА зала.** Вошедший по паролю — сотрудник или
владелец: у него рабочий инструмент, чтобы у полки и за кассой быстро найти
товар, его коды, остаток и поставщика. Зашедший без пароля — **покупатель**
(решение владельца): ему каталог показывается списком без фото — название,
код, цена, наличие и когда завезли, плюс список покупок, карточка магазина,
«сообщить, когда появится», «что подешевело» и «сегодня привезли».
Раньше здесь было записано обратное («не проектируй для покупателя») — это
устарело, владелец решение поменял.

**Что при этом не изменилось.** Ссылка публичная — открыть её может кто
угодно, поэтому без входа не показываем: **закупочные цены, остаток числом,
продажи, поставщиков и их контакты, цены чужих магазинов**. Названия, коды товара, артикул и штрихкоды —
наоборот, смысл приложения, они видны сразу. **Розничная цена тоже открыта** —
решение владельца 2026-08-13: ценник и так висит в зале (см. `08-CATALOG.md`,
врезка «Для кого это приложение»).

Проверяется по `state.session` / `state.canPurchase`. Сервера больше нет, а
значит и защиты «на сервере» нет: **единственная настоящая граница — что
попадает в открытый файл витрины** (`buildPublicProducts`). Достаточно
положить туда лишнее поле — и данные утекут, даже если в интерфейсе они нигде
не показаны. Всё закрытое живёт только в зашифрованных файлах.

## Устройство кода (с 2026-08-13)

Приложение разложено на **25 модулей** в `catalog/js/modules/`, подключается
как `<script type="module" src="js/modules/app.js">`. Сборщика нет — браузер
грузит модули сам.

| Модуль | За что отвечает |
|--------|-----------------|
| `store` | состояние `state`, общий изменяемый `ui`, кэш на устройстве |
| `brand` | оформление под конкретный магазин: имя, логотип, цвет, что включено |
| `parts` | нарезка каталога на куски, подписи содержимого, заливка пачками |
| `core` | `$`, `esc`, `norm`, форматы, шторки, уведомления |
| `icons` | набор контурных значков (эмодзи в интерфейсе запрещены) |
| `catalog` | категории, раскладка товара, умный поиск |
| `render` | сетка, разделы нижней панели, фильтры, ленты |
| `card` | карточка: цены, остаток, калькулятор, поставщики |
| `publish` | шифрование, снимки, публикация на GitHub, вход по паролю |
| `imports` | разбор файлов 1С и слияние в каталог |
| `orders` | заказы поставщикам: календарь неделя/месяц, просрочка |
| `work` | вкладка «Работа»: дела смены и состояние в одном месте |
| `restock` | «закончилось на полке»: список пополнения, заказ из него |
| `compare` | сравнение нескольких товаров: цены поставщиков рядом |
| `guest` | покупатель: карточка магазина, связь, подсказки о ценах |
| `shopping` | список покупок: количество, сумма, смахивание строки |
| `news` | «появилось», «подешевело», новинки — считает сам телефон |
| `mascot` | волк-талисман: приветствие, подсказки, отклик, пустые экраны |
| `photos`, `admin`, `competitors`, `device`, `scanner`, `data` | по названию |
| `app` | связывание обработчиков и запуск |

⚠️ **Записи сотрудника живут на его телефоне.** Писать в общий каталог может
только владелец (ключ публикации у него), поэтому заказы (`wm_orders_local_v1`)
и список пополнения (`wm_restock_v1`) лежат в `localStorage` и уходят владельцу
текстом по кнопке «Передать». Любую такую запись ограничивай по объёму и сроку
(300 строк, заказанное живёт две недели) — иначе телефон копит мусор.
Заказы и список пополнения связаны **обратным вызовом** (`prefill.onSaved`), а не
встречными импортами: круговые импорты тест `modules` не ловит, а ломаются они
молча.

⚠️ **Что известно про выгрузки 1С этого магазина** (разбор 13 файлов,
28.08.2026). Выгружаются раз в день около 17:40. Опорные отчёты: «Цены
поставщиков» (24 818 строк, 668 поставщиков, **колонка «Период» = настоящая
дата поступления**), «Остатки номенклатуры» (10 673 товара), «Прайс-лист»
(18 215), справочник штрихкодов (21 187). Чего в 1С НЕТ: **описания товара,
массы нетто, габаритов** — колонки есть, но пустые целиком. Вес написан в
названии у 78% товаров, оттуда его и берёт `unitPriceText`. **Колонке
«Процент наценки» из 1С доверять нельзя** — считать наценку самим из двух
цен. Отчёт «Неликвидные товары» строится ЗА ПЕРИОД и после его конца
завозов не видит: дату оттуда брать только если она новее.

⚠️ **«Обновлено вчера в 17:40».** Данные покупателю всегда суточной
давности: владелец выгружает из 1С и публикует раз в день вечером. Подпись
(`updatedText` в `catalog.js`, из `state.showcaseAt` = `savedAt` описи
витрины) стоит в карточке, на ценнике и в карточке магазина, и сохраняется
в кэш вместе с каталогом. Не убирать: она держит честность всего
покупательского раздела — без неё «есть в магазине» читается как «есть
прямо сейчас».

⚠️ **Штрихкод с весов.** Весы магазина печатают EAN-13 вида
`23` + пять цифр кода товара + пять цифр ВЕСА В ГРАММАХ + контрольная цифра
(разобрано по настоящей этикетке: `2305940003301` = код 5940, 330 г).
Разбор — `parseScaleBarcode` в `catalog.js`, поиск — `findByBarcode` в
`scanner.js`. Догадку принимаем только при трёх совпадениях: контрольная
цифра, код есть в каталоге, вес 10 г…30 кг. Префикс держится списком
`SCALE_PREFIX` — появятся вторые весы, добавится строка. Осторожно:
внутренние коды магазина `28…` тоже начинаются с двойки.

⚠️ **Ценник — покупательский экран, у сотрудника его нет** (кроме весовой
этикетки: по ней сотрудник видит вес и сумму — решение владельца)**.** Сканер у
покупателя всегда работает в режиме ценника (`scanToPrice`), переключатель
`#scanModeSeg` ему не показывается; у сотрудника режимы только «Товар» и
«Закончилось». Состав ценника (цена и за что она, наличие словом, дата
поступления, описание, раздел, код) закреплён проверками в `tests/guest.js` —
менять его можно, но проверки надо править вместе с ним.

⚠️ **Правку витрины проверяй по опубликованным файлам, а не по коду.**
Между кодом и покупателем есть звено, которое я не контролирую: витрину
собирает телефон владельца, и там может работать сохранённая старая версия.
Так и вышло 27.08 со штрихкодами — публикация прошла успешно и без них.
Поэтому: (1) добавил поле в `PUBLIC_FIELDS` — подними `SHOWCASE_V` в
`publish.js`, тогда приложение владельца само попросит опубликовать заново;
(2) после его публикации посмотри сами файлы:
`curl -s https://dexauron.github.io/Auron/catalog/data/index.json` и любой
кусок `data/p/00.json?h=<подпись>` — поле на месте или нет.

⚠️ **Волк и движение — «в меру» (слово владельца).** Талисман магазина
(`icons/wolf.png` 150 px и `icons/wolf-head.png` 96 px — палитровые PNG на
13 и 6 КБ) живёт в шапке, на пустых экранах и в облачке-реплике. Правила,
которые нельзя нарушать: здоровается раз в день, реплика не чаще раза в
6 секунд (остальное уходит обычным `toast`), **в рабочих окнах (заказы,
«закончилось», сравнение) его нет вовсе**, выключается в настройках устройства
(класс `no-wolf`), замирает при `low-power` и `prefers-reduced-motion`.
Всё движение — только `transform`/`opacity`; отклик на касание мягкий
(сжатие 0.96–0.99, без пружины с перелётом). Тексты волка не должны содержать
названия магазина — это проверяет тест `store-config`, адрес и часы берутся
из `js/config.js`.

⚠️ **Скорость — на бюджетном Android, а не на своём компьютере.** Замеры делать
с процессором в 6 раз медленнее (`Emulation.setCPUThrottlingRate`), каталог от
12 000 товаров. Правила, выведенные из аудита 2026-08-26:
- ничего не считать «заранее для всех товаров» — только по требованию и
  порциями в свободную минуту (`requestIdleCallback` с запасным `setTimeout`);
- поиск не перебирает каталог: сначала кандидаты из указателя `wordIndex()`,
  дорогой разбор опечаток — отдельным проходом и только когда нашлось мало;
- `localeCompare` на больших списках заменять общим `cmpRu` (Intl.Collator),
  даты сравнивать `cmpStr`;
- тяжёлое (запись кэша, разбор файлов 1С) — прочь с горячего пути: idle или
  отдельный поток;
- `backdrop-filter` — самая дорогая красота на Android: под классом `.low-power`
  всё размытие выключается (телефон с ≤4 ГБ памяти);
- планку держат `tests/speed.js` (потолки в миллисекундах) и
  `tests/search-quality.js` (выдача поиска не должна меняться от ускорений).

⚠️ **Мёртвый код опаснее лишнего.** Дважды находили вызовы функций, которых нет:
они не падают, пока человек не дойдёт до кнопки. Поэтому: удаляя возможность,
удаляй ВСЁ — разметку, обработчики, стили, поле состояния; а после правок гоняй
`tests/lint.js` (разбор кода без запуска, ловит обращения к несуществующему).

⚠️ **Размер кнопок меряй при ОТКРЫТЫХ окнах.** Проверка вёрстки осматривает
каждое окно с настоящим содержимым: при закрытых окнах кнопки нулевого размера
и мелкие цели проезжают незамеченными.

**Правила, которые проверяет тест `modules`:** импортировать только то, что
используется; экспортировать только то, что кому-то нужно; ни один модуль не
больше 1200 строк; офлайн-кэш в `sw.js` знает про все модули.

⚠️ **Общее изменяемое состояние — только через объект `ui` из `store.js`.**
Модуль не может присвоить чужой переменной (`import` даёт лишь чтение), а полю
объекта — может. Новую общую переменную заводи полем `ui`, а не `let` в модуле.

## Рабочий цикл (делай в этом порядке)

1. **Правь `catalog/`** на рабочей ветке каталога (сейчас
   `claude/catalog-db-migration-6wkhuv`).
2. **Прогони тесты** — см. раздел «Тесты». Обязательно перед коммитом.
3. **Бампни кэш SW**: в `catalog/sw.js` подними `wm-catalog-vNN` на +1. Без этого
   у пользователей останется старая версия. Фото-кэш `wm-photos-v1` не трогай.
4. **Коммить и пуш** в рабочую ветку каталога.
5. **Зазеркаль в деплой-ветку** — см. «Деплой». Без этого изменения не попадут
   на сайт.
6. **Запиши решение** одной строкой в `docs/DECISIONS.md` (что и почему,
   словами владельца). Каталожные решения делегированы — тяжёлую документацию
   вести не нужно, хватает строки в журнале.

## Деплой (двухветочный — не перепутай)

Сайт на GitHub Pages собирается воркфлоу `.github/workflows/deploy.yml` из **двух
независимых источников**:
- приложение Auron — ветка `claude/optimistic-einstein-Afzmv` (папка `app/`);
- **каталог — ветка `claude/store-product-catalog-60wer4` (папка `catalog/`)**.

Деплой каталога запускается **пушем в `claude/store-product-catalog-60wer4`**.
Если разработка идёт в отдельной ветке (как сейчас), нужно **зеркалировать**
папку `catalog/` в деплой-ветку отдельным коммитом. Готовый скрипт:

```bash
bash .claude/skills/catalog-dev/scripts/deploy-mirror.sh "текст коммита"
```

Он через `git worktree` копирует текущую `catalog/` в деплой-ветку, коммитит
`deploy: …` и пушит. Меняешь сам `deploy.yml` — синхронизируй его в ОБЕ ветки.
Живой сайт: https://dexauron.github.io/Auron/catalog/

## Публикация данных (вместо базы)

Схемы базы больше нет — менять «структуру» значит менять то, что кладут в
файлы. **Каталог публикуется КУСКАМИ** (с 2026-08-13): переписываются только
изменившиеся куски, а не весь каталог.

- Открытая витрина: куски `data/p/00.json…` + опись `data/index.json`
  (подпись содержимого каждого куска). Старый цельный `products.json` только
  читается — на случай, если опись ещё не опубликована.
- Закрытая часть: `catalog.enc` — зашифрованная **опись** (мелочь внутри неё),
  товары/цены/продажи — кусками в `data/sec/`. Каталог ОДИН на всех ролей;
  второй копии для сотрудника больше нет.
- **Ключ каталога** случайный, лежит в `keys.json` под каждым паролем отдельным
  конвертиком. Отсюда: роль определяется тем, чей конвертик открылся
  (`unlockAny`); новая роль стоит полкилобайта; ключ НЕ выводится из пароля,
  поэтому обычная публикация не перешифровывает каталог.
- **Смена любого пароля меняет ключ каталога и переписывает всё** (`rotate`).
  Это не расточительство: прежний `keys.json` остаётся в истории репозитория
  навсегда, поэтому без нового ключа знавший старый пароль открывал бы каталог
  и дальше. Так работают обе смены — пароля сотрудника и пароля владельца
  (меню → «Пароль каталога (ваш)»).
- Номер куска — стабильный хэш от id (`parts.js`), а не позиция в списке:
  иначе один новый товар сдвинул бы границы всех кусков.
- В адресе куска стоит его подпись (`?h=…`) — service worker кэширует такие
  адреса «сначала кэш» (кэш `wm-data-v1`, переживает обновление приложения).
- **Первый заход показывает товары по мере загрузки** (`progressiveShow` в
  `imports.js`): куски витрины не ждут друг друга. Пересборка поискового
  индекса — не чаще раза в полсекунды, иначе телефон захлёбывается. При
  повторных заходах каталог и так показывается из кэша устройства (`init`).
- `buildPublicProducts()` — что уходит в **открытую** витрину. Каждое новое
  поле здесь публичное, см. раздел про приватность.
- Запись в репозиторий — `ghCommit()` одним деревом (`content: null` удаляет
  файл, `onProgress` показывает ход). Публикует только владелец со своего
  устройства (у него есть токен).
- **Деплой не должен выкладывать закрытые куски на сайт:** в `deploy.yml`
  удаляются и `data/*.enc`, и папки `data/sec`, `data/sec-staff`.
- Старые данные должны читаться новым кодом: каталог старого формата (два
  цельных файла `secret-catalog.enc` / `secret-staff.enc`) открывается как
  раньше и удаляется при первой же публикации — проверяет тест `publish-parts`.

## Тесты (Playwright, живут в репозитории)

Тесты лежат в `catalog/tests/` (не во временной папке — она обнуляется вместе
с контейнером). Подробности — `references/testing.md`.

```bash
# один раз за сессию — статический сервер из папки catalog
python3 -m http.server 8123 --directory catalog &

# весь набор
NODE_PATH=/opt/node22/lib/node_modules node catalog/tests/run.js
# одна проверка
NODE_PATH=/opt/node22/lib/node_modules node catalog/tests/navigation.js
```

Ключевое, что легко забыть и сломать:
- **Порядок моков** в `helpers.js`: `js/config.js` подменяется ПЕРВЫМ, иначе
  настоящие настройки перезапишут подставленные и тест уйдёт на живой магазин.
- Мобильный вьюпорт (390×900, `isMobile:true`), `serviceWorkers:'block'`.
- Проверять надо **данные, а не картинку**: приложение отдаёт наружу
  `window.WM_PUBLISH` (только на localhost) — там `_state()`, `_cat()`,
  `buildPublicProducts()` и прочее. Утечку в витрину ловят по выходу
  `buildPublicProducts()`, а не по тому, что видно на экране.
- **Тест, который никогда не падал, ничего не доказывает.** Новую проверку
  прогоняй на старом коде (`git stash`) и убеждайся, что она валится.
- **`audit`** — разметка: кнопка без обработчика, ссылка на исчезнувший
  элемент, забытый элемент, эмодзи в разметке. Гоняй после каждой переделки
  экранов: именно там заводятся молчащие кнопки.
- **`layout`** — вёрстка на 320 и 390 px: ничего не вылезает за край, кнопки не
  мельче пальца (44 px; исключения — переключатель iOS 51×31 и галочка внутри
  строки-во-всю-ширину).
- ⚠️ **Не пиши в строку списка через `textContent`** — внутри `<span>` с
  названием, и он сотрётся. Есть `setRowText(id, text)` в `core.js`.

После правок гоняй ВЕСЬ набор, а не только новый тест.

## Частые ориентиры в коде

- `store.js` — `state` (товары, фильтры, режимы) и `ui` (общее изменяемое).
- `render.js` — `visibleProducts()` (вся цепочка фильтров/поиска/сортировки,
  сюда добавляют новые фильтры), `renderAll()` (общий перерисовщик, зови после
  изменения состояния), `renderGrid()`.
- `card.js` — `openProduct(p)`, цены поставщиков, остаток и «сколько заказать»,
  калькулятор предложения.
- `core.js` — `openSheet/closeSheet/restackSheets`: «шторки» с историей
  телефона и порядком наложения.
- `catalog.js` — категории и раскладка товара по названию (`productCategory`).
- Данные устройства (избранное, недавние, тема, настройки) — `localStorage`,
  ключи с префиксом `wm_`; крупный кэш каталога — IndexedDB (`store.js`).
