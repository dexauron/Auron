# Разработка каталога (Way Market · Каталог)

Каталог — **отдельное приложение** внутри репозитория Auron. Своя база, свои
ветки, свой деплой. С кодом и базой основного приложения Auron (`app/`) НЕ
смешивать. Владелец — не программист; общение и все тексты в интерфейсе — на
русском, простым языком.

## Что это за приложение

- **Одностраничное приложение (SPA) на ванильном JS**, без фреймворков. Вся
  логика — в `catalog/js/app.js` (одна большая IIFE, ~4500 строк, объект
  `state`). Разметка — `catalog/index.html`, стили — `catalog/styles.css`.
- **Бэкенд: self-hosted Supabase** (PostgreSQL + Auth + PostgREST + Storage) на
  российском VPS. Ключи и URL — `catalog/js/config.js` (anon-ключ **публичный**,
  его коммитить можно; service_role-ключ и пароли — НИКОГДА, только в чате).
- **PWA**: `catalog/sw.js`. Кэш фронта — `wm-catalog-vNN`, фото — `wm-photos-v1`
  (вечный, не чистится).
- **Роли**: Владелец/админ · Менеджер (аналитик) · Кассир — через `catalog_roles`
  и функции `catalog_my_role()`, `catalog_is_admin()`, `catalog_can_purchase()`.
  Покупатель без аккаунта = `anon`.

## ⚠️ Приватность — главное правило данных

Покупатель **без входа** видит только «витрину магазина»: товары, розничную
цену, фото, описание, категорию. Он **НЕ должен видеть** внутренние данные:
поставщиков, закупочные цены, контакты, штрихкоды/коды кассы, поступления,
аналитику продаж. Проверяется по `state.session` / `state.canPurchase`, а на
сервере — политиками RLS. Любая новая фича, показывающая данные, должна
уважать это разделение. Разделы «только для сотрудников» помечаются классами
`.emp-only` / `.purchase-only` и скрываются в `renderAll()` для анонима.

## Рабочий цикл (делай в этом порядке)

1. **Правь `catalog/`** на рабочей ветке каталога (сейчас
   `claude/catalog-db-migration-6wkhuv`).
2. **Прогони тесты** — см. раздел «Тесты». Обязательно перед коммитом.
3. **Бампни кэш SW**: в `catalog/sw.js` подними `wm-catalog-vNN` на +1. Без этого
   у пользователей останется старая версия. Фото-кэш `wm-photos-v1` не трогай.
4. **Коммить и пуш** в рабочую ветку каталога.
5. **Зазеркаль в деплой-ветку** — см. «Деплой». Без этого изменения не попадут
   на сайт.
6. **Запиши решение** одной строкой в `docs/DECISIONS.md` (что и почему,
   словами владельца). Каталожные решения делегированы — тяжёлую документацию
   вести не нужно, хватает строки в журнале.

## Деплой (двухветочный — не перепутай)

Сайт на GitHub Pages собирается воркфлоу `.github/workflows/deploy.yml` из **двух
независимых источников**:
- приложение Auron — ветка `claude/optimistic-einstein-Afzmv` (папка `app/`);
- **каталог — ветка `claude/store-product-catalog-60wer4` (папка `catalog/`)**.

Деплой каталога запускается **пушем в `claude/store-product-catalog-60wer4`**.
Если разработка идёт в отдельной ветке (как сейчас), нужно **зеркалировать**
папку `catalog/` в деплой-ветку отдельным коммитом. Готовый скрипт:

```bash
bash .claude/skills/catalog-dev/scripts/deploy-mirror.sh "текст коммита"
```

Он через `git worktree` копирует текущую `catalog/` в деплой-ветку, коммитит
`deploy: …` и пушит. Меняешь сам `deploy.yml` — синхронизируй его в ОБЕ ветки.
Живой сайт: https://dexauron.github.io/Auron/catalog/

## Миграции базы (ОБНОВЛЕНИЕ-NN.sql)

Схему базы правит только владелец вручную в Supabase Studio. Поэтому изменение
схемы оформляется как **новый файл-инструкция**, а не применяется кодом:

1. Создай `catalog/setup/ОБНОВЛЕНИЕ-<N+1>.sql` (N — максимальный существующий).
   Формат — шапка с датой, «Зачем» простыми словами и «Как применить», затем
   идемпотентный SQL (`create table if not exists`, `create or replace function`,
   `drop policy if exists` перед `create policy`). Образец и правила —
   `references/migrations.md`.
2. **Продублируй тот же блок** в конец трёх сводных файлов, разделителем
   `-- ═══ ОБНОВЛЕНИЕ-NN ═══`: `catalog/setup/ВСЕ-ОБНОВЛЕНИЯ.sql`,
   `catalog/setup/НОВАЯ-БАЗА.sql`, `catalog/setup/schema.sql`.
3. Доступ для покупателя (`anon`) к данным — только через `security definer`
   функции с `grant execute … to anon`, напрямую в таблицы `anon` не пишет.
4. В клиенте новые вызовы делай **защищёнными**: если миграция ещё не применена
   (таблицы/функции нет), фича должна тихо не работать, а приложение —
   продолжать как раньше (оборачивай в try/catch, ошибку игнорируй). Напомни
   владельцу в ответе, что нужно выполнить `ОБНОВЛЕНИЕ-NN.sql`.

## Тесты (Playwright с моками Supabase)

Тесты гоняются локально против замоканной базы — реальный бэкенд не нужен.
Правила окружения и моков подробно — `references/testing.md`. Быстрый старт:

```bash
# сервер статики из папки catalog (в фоне)
cd catalog && python3 -m http.server 8123 &
# запуск теста (модули Playwright лежат в системном NODE_PATH)
NODE_PATH=/opt/node22/lib/node_modules node <тест>.js
```

Ключевое, что легко забыть и сломать:
- **Порядок роутов**: Playwright матчит роуты в порядке «последний зарегистрирован
  — первый проверяется». Поэтому **широкие ловушки** (`**/rest/v1/**`,
  `**/rest/v1/rpc/**`) регистрируй ПЕРВЫМИ, а конкретные (`**/rest/v1/catalog_products*`)
  — ПОСЛЕ них, иначе ловушка перехватит всё.
- Мобильный вьюпорт (`viewport:{width:390,height:844}, isMobile:true`),
  `serviceWorkers:'block'`.
- Ответ на `select=id` у `catalog_products` — статус 206 с заголовком
  `content-range: 0-0/<всего>` (так приложение узнаёт общее число товаров).
- Стартовый шаблон теста со всеми стандартными моками:
  `assets/test-template.js` — копируй его и дописывай проверки.

После правок **прогоняй весь набор регрессов**, не только новый тест. Типичный
набор в рабочей папке: `filters2 arrival2 emp anon fixbug catcheck suggest fill
stack responsive smart share fav popular`. Каждый печатает `=== … ОК ===` в
конце при успехе.

## Частые ориентиры в app.js

- `state` — единый объект состояния (товары, фильтры, сессия, режимы).
- `visibleProducts()` — вся цепочка фильтров/поиска/сортировки; сюда добавляют
  новые фильтры. `sortList()` — порядок сортировки.
- `renderAll()` — общий перерисовщик (чипы, ленты, сетка); зови после изменения
  состояния. `renderGrid()` — сетка товаров.
- `openProduct(p)` — карточка товара. `openSheet/closeSheet/restackSheets` —
  система «шторок» (окон) с историей телефона и z-index по порядку открытия.
- Данные, специфичные для устройства (избранное, недавно смотрели, тема) —
  в `localStorage`, ключи с префиксом `wm_`.
