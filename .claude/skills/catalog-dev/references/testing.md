# Тесты каталога — окружение и моки Supabase

Тесты — это одиночные Node-скрипты на Playwright, которые открывают приложение в
браузере против **замоканной** базы. Реальный Supabase не нужен.

## Окружение

- Модули Playwright — в системном пути: запускай с
  `NODE_PATH=/opt/node22/lib/node_modules node <тест>.js`.
- Приложение раздаётся статикой из папки `catalog`:
  `cd catalog && python3 -m http.server 8123 &` (порт 8123).
- Браузер — Chromium уже установлен (`playwright install` не запускать).
- Всегда мобильный контекст: `viewport:{width:390,height:844}, isMobile:true,
  hasTouch:true, serviceWorkers:'block'`.

## Моки: порядок роутов — критично

Playwright проверяет зарегистрированные роуты в порядке **«последний
зарегистрирован — проверяется первым»**. Поэтому:

1. Сначала — широкие ловушки: `**/auth/v1/**`, `**/rest/v1/**`,
   `**/rest/v1/rpc/**` (возвращают `{}` или `[]`).
2. Потом — конкретные: `**/rest/v1/catalog_groups*`,
   `**/rest/v1/catalog_suppliers*`, `**/rest/v1/catalog_products*`,
   `**/rest/v1/rpc/catalog_<имя_функции>*`.

Если конкретный роут зарегистрировать раньше ловушки — ловушка перехватит запрос
и тест «не увидит» данные. Это самая частая причина ложных падений.

## Особые ответы, которые ждёт приложение

- **`catalog_products?select=id`** — приложение так узнаёт общее число товаров.
  Отвечай статусом **206** с заголовком `content-range: 0-0/<всего>` и пустым
  телом. Обычный запрос товаров — 200 + JSON-массив (со срезом по offset/limit).
- **PostgREST-срез**: читай `offset`/`limit` из URL и режь массив (см. `slice()`
  в шаблоне) — иначе пагинация/докачка в тесте поведёт себя не как в проде.
- **RPC-вызовы** (`sb.rpc('name', args)`) — это POST на
  `**/rest/v1/rpc/name`. Чтобы проверить аргументы, читай `q.postData()`.

## Приём: захват вызова RPC

```js
let tracked = null;
await ctx.route('**/rest/v1/rpc/catalog_track_view*', (r, q) => {
  try { tracked = JSON.parse(q.postData() || '{}'); } catch (e) {}
  r.fulfill({ status: 200, contentType: 'application/json', body: 'null' });
});
// … действие в UI …
chk(tracked && tracked.p_product_id === id, 'просмотр учтён: ' + JSON.stringify(tracked));
```

## Роли и приватность в тестах

- Аноним (по умолчанию) — `auth/v1` отдаёт `{}`, сессии нет. Проверяй, что
  разделы `.emp-only` / `.purchase-only` скрыты, поставщики/закупки недоступны.
- Чтобы сымитировать вошедшего сотрудника, замокай `catalog_my_role` (RPC) на
  нужную роль и подсунь сессию; но проще многие проверки делать напрямую через
  `page.evaluate`, форсируя показ разделов, — смотри существующий `emp.js`.

## Соглашение об успехе

Каждый тест печатает `OK:`/`FAIL:` по проверкам и в конце `=== … ОК ===` при
полном успехе, `process.exit(1)` при падении. После правок гоняй ВЕСЬ набор
регрессов, а не только новый тест.
