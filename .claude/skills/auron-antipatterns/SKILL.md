# Auron — как НЕ надо (и как надо)

Учимся на примерах ошибок. Каждый пункт — реальная ловушка этого проекта: слева как делают
и ломают, справа как правильно. Это про ВАШ код — чтобы не наступать на грабли, а не про
чужие системы.

## 1. Деньги во float

❌ **Неправильно:**
```js
const total = 155.50;            // рубли во float
const withTax = total * 1.2;     // 186.6? 186.59999999999999?
```
Плавающая точка теряет копейки. В финансовом приложении это недопустимо.

✅ **Правильно:** копейки в целых (bigint), деление на 100 только на экране.
```js
const total_kopecks = 15550;     // всегда целое
// показ: (total_kopecks/100).toLocaleString('ru-RU') + ' ₽'
```
Подробно — skill `auron-money-format`.

## 2. DELETE / UPDATE по финансовому реестру

❌ **Неправильно:** «исправлю проводку, поменяю сумму» — `UPDATE journal_lines ...` или
удаление строки. Так теряется история и рушится баланс.

✅ **Правильно:** реестр неизменяем. Ошибка — **сторно** (обратная проводка,
`is_reversal=true`, `reversal_of→исходная`). Бизнес-объект — мягкое удаление `deleted_at`.
Подробно — skill `auron-double-entry`.

## 3. Изоляция магазинов «на клиенте»

❌ **Неправильно:** думать, что `.eq('org_id', currentOrg)` в запросе защищает данные.
Клиентский фильтр можно убрать — и увидеть чужой магазин.

✅ **Правильно:** изоляция — это **RLS в PostgreSQL**. Пользователь физически не прочитает
чужой `org_id`, даже прямым запросом. Клиентский фильтр — для удобства, не для защиты.
Подробно — skill `auron-rls-roles`.

## 4. Проверка доступа по имени роли

❌ **Неправильно:** `if (role.name === 'Бухгалтер') { ... }`. Имена ролей
пользовательские, владелец создаёт свои — проверка развалится.

✅ **Правильно:** проверять по **permission-ключу** (`shift.close`, `edit_cash`), а не по
имени роли.

## 5. Забытый client_uuid → двойные операции

❌ **Неправильно:** отправлять новую транзакцию без `client_uuid`. Двойной тап или
переотправка при переподключении → две одинаковые операции, задвоённые деньги.

✅ **Правильно:** каждая операция ввода несёт `client_uuid`, сервер отклоняет дубликат.
Подробно — skill `auron-offline-sync`.

## 6. Правки задним числом в закрытом периоде

❌ **Неправильно:** «по-тихому поправлю прошлый месяц». Закрытый/`locked` период трогать
нельзя даже администратору.

✅ **Правильно:** через `correction_requests` — причина → одобрение владельца → сторно +
новая проводка. Всё видно.

## 7. Ввод операций офлайн

❌ **Неправильно:** дать вводить операции без сети «а потом синхронизируем». По архитектуре
офлайн = **только просмотр**, иначе получаем конфликты записи.

✅ **Правильно:** офлайн блокирует ввод с понятным сообщением; не ушедшее — в `offline_queue`.

## 8. Забыл бампнуть версию кэша

❌ **Неправильно:** поменял фронт, версию `auron-vNN` в `sw.js` не тронул. У пользователя
осталась старая версия — «я всё поменял, а на сайте старое».

✅ **Правильно:** любое изменение фронта → `auron-vNN` +1. Подробно — skill `auron-pwa-deploy`.

## 9. Смешал Auron и каталог

❌ **Неправильно:** обращаться к базе/ключам каталога из кода Auron (или наоборот). Это
**разные приложения с разными базами**.

✅ **Правильно:** `app/` (Auron) и `catalog/` — раздельно. Ключи каталога в
`catalog/js/config.js`, деплой собирает из двух веток. Подробно — skill `auron-pwa-deploy`.

## 10. Хардкод вместо конфига

❌ **Неправильно:** захардкодить список статей расходов, обязательность полей, формулу
маржи. Каждый магазин настраивает под себя.

✅ **Правильно:** «конфигурация вместо кода» — справочники, обязательные поля, формулы,
состав отчётов живут в настройках/JSONB, не в коде. Кастомные поля — в `custom_fields`.
