# Auron — офлайн, синхронизация, конфликты

Это утверждённые архитектурные решения из `docs/05-ARCHITECTURE.md`. Не менять их
по своему усмотрению — только по решению владельца, зафиксированному в документе.

## Главное правило офлайна: ТОЛЬКО ПРОСМОТР

Нет интернета → приложение работает в режиме чтения. Данные, загруженные до обрыва,
доступны для просмотра. **Ввод новых операций заблокирован** с понятным сообщением:

```
⚠️ Нет соединения
Данные на 14:32 — просмотр доступен
Ввод операций будет доступен при восстановлении сети
```

Почему так: если запись офлайн запрещена, то одновременная запись в одну запись с двух
устройств физически невозможна → конфликтов почти нет. Это сознательный размен простоты
на надёжность в приложении, работающем с деньгами.

## Кэш: Service Worker + stale-while-revalidate

- `sw.js` кэширует последние загруженные данные.
- Стратегия **stale-while-revalidate**: при открытии сразу показываем кэш, в фоне тянем
  свежее и обновляем.
- Версию кэша `auron-vNN` бампать при каждом изменении фронта (иначе у пользователя
  останется старая версия). Это отдельное правило — см. skill `auron-pwa-deploy`.

## Идемпотентность: client_uuid

Каждая операция, создаваемая на клиенте, несёт `client_uuid` (генерируется на клиенте).
Сервер **отклоняет дубликат** по этому полю. Это защита от:
- двойного нажатия кнопки,
- повторной отправки при переподключении.

Таблица `transactions` уже имеет `client_uuid(unique)`. Любая новая операция ввода должна
следовать этому же паттерну.

## Очередь неотправленного: offline_queue

Таблица `offline_queue` (Домен 15) — черновики, не успевшие уйти (например, телефон умер
посреди ввода):

```
offline_queue: id · org_id · user_id · device_id
  · operation_type · payload(JSONB)
  · client_uuid  ← идемпотентность при синхронизации
  · created_at_local · synced_at
  · status(pending|synced|failed|conflict)
```

Черновик доедет при следующем подключении, дубликат исключён через `client_uuid`.

`sync_log` — журнал синхронизаций устройств (когда, сколько записей, статус). Если у
кассира и бухгалтера разошлись данные — по нему видно когда и на каком устройстве.

## Реальное время: Realtime WebSocket

3+ человека в одном магазине. Когда сотрудник вводит операцию — бухгалтер и владелец
видят изменение **без перезагрузки**. Realtime WebSocket (self-hosted, встроен в стек
Supabase) шлёт событие всем устройствам организации. UI оптимистичный: показываем сразу,
затем подтверждаем с сервера.

## Разрешение конфликтов: last-write-wins

Конфликты почти исключены (офлайн = чтение). Если всё же два устройства записали разное —
**побеждает более поздняя по timestamp** (last-write-wins). Для финансовых операций это
приемлемо, потому что реестр неизменяемый: ошибочная запись исправляется сторно, а не
перезаписью (см. skill `auron-double-entry`).

## Чек-лист при работе с этим доменом

- [ ] Ввод офлайн заблокирован, показано сообщение с временем последних данных
- [ ] Новая операция несёт `client_uuid`, сервер проверяет уникальность
- [ ] Не успевшее уйти — в `offline_queue` со `status=pending`
- [ ] При переподключении очередь отправляется, дубликаты отсекаются по `client_uuid`
- [ ] Изменения прилетают другим устройствам через Realtime, без перезагрузки
- [ ] Версия кэша `auron-vNN` увеличена, если менялся фронт
