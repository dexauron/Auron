# Перенос на другую платформу

## Зачем переезжать

Не ради моды. Три причины по существу:

1. **Данные видны сотруднику.** Чтобы человек работал в приложении, ему
   выдаётся доступ к Google-таблице. Роли ограничивают приложение, но не
   файл. Полная изоляция возможна только на своём сервере.
2. **6 минут на операцию.** Импорт из 1С на 16 500 позиций упирается в
   лимит; любая тяжёлая аналитика — тоже.
3. **Нельзя нормально разрабатывать.** Один файл на 13 800 строк без
   сборки и без модулей. Дальше будет только хуже.

## Что переносится как есть

- **Вся логика денег.** Формулы дня и месяца, сверка кассы, долги,
  наценка — это чистые функции, они не зависят от платформы. Их стоит
  перенести первыми и с теми же тестами: тесты уже написаны на реальных
  числах владельца.
- **Модель данных** — см. `02-DATA-MODEL.md`, схема готова.
- **Тексты интерфейса** — они выверялись под непрограммиста, переписывать
  заново незачем.
- **Правила поведения**: замок периода, «своё и только сегодня», корзина
  30 дней, офлайн-очередь, защита от повторной отправки. Это опыт,
  оплаченный ошибками; выкидывать нельзя.

## Что придётся переписать

| Что | Почему |
|---|---|
| Всё обращение к `SpreadsheetApp` | заменяется на SQL |
| `_withLock` | вместо него транзакции БД |
| `CacheService` | Redis или обычный кэш приложения |
| Авторизация через Google-аккаунт | своя: почта+пароль или OAuth |
| `google.script.run` | обычный HTTP (REST или tRPC) |
| Один `Index.html` | разбить на компоненты |

## Рекомендуемый стек

Ставлю на **скучный и распространённый**, чтобы любой разработчик мог
подхватить:

- **База:** PostgreSQL.
- **Сервер:** Node.js (NestJS или Fastify) либо Python (FastAPI) — что
  ближе тому, кто будет делать.
- **Фронт:** React или Vue + Vite. Мобильный вид — тот же сайт (PWA);
  отдельное мобильное приложение до первой сотни магазинов не нужно.
- **Хостинг:** любой VPS. Данные российского магазина — держать в РФ.

Не советую: серверless-БД с посуточной оплатой запросов (учёт читает
много и часто), микросервисы (для одного магазина это карго-культ),
GraphQL (усложнит без выгоды на этом объёме).

## Порядок переезда

1. **Схема БД + перенос данных.** Выгрузить листы, залить в таблицы,
   сверить итоги: остатки счетов, долг поставщикам, выручка за месяц
   должны совпасть до рубля со старым приложением.
2. **Перенести расчёты и тесты.** Пока без интерфейса. Тесты зелёные на
   настоящих данных — значит логика не потеряна.
3. **Сервер и права.** Роли, замок периода, аудит — до интерфейса, иначе
   потом «допишем» и не допишем.
4. **Интерфейс по экранам.** Порядок по важности: приём кассы → накладные
   → главная → поставщики → товары → отчёты → настройки.
5. **Параллельная работа две недели.** Магазин ведёт учёт в обеих
   системах, цифры сверяются ежедневно. Только после этого переключение.

Шаг 5 не пропускать. Учёт денег нельзя переключать «в один день».

## Оценка

Разработчик, работающий один, полный рабочий день: **2–3 месяца** до
паритета с нынешним. Половина времени — не код, а сверка данных и мелочи
поведения, которые здесь уже вылизаны.
