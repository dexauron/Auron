# 08 — Варианты технической архитектуры (на вырост)

> Статус: 🔄 черновик для обсуждения. Не отменяет `05-ARCHITECTURE.md` (это *целевая* модульная модель) — здесь про то, **на чём физически работает приложение** и когда что менять.
>
> ⚠️ Сейчас менять ничего не нужно. Это план «на вырост». Порог переезда — в конце документа.

---

## Что есть сейчас (Вариант A — «Google»)

```
Телефон/ПК ──> Google Apps Script (Code.gs) ──> Google Таблицы (данные)
              один файл Index.html (~7000 строк) — весь фронт
```

- ✅ Бесплатно, данные у владельца на его Google-Диске, ноль администрирования
- ✅ Идеально для одного магазина и старта
- ❌ Таблицы — не база данных: тормозят на десятках тысяч операций, лимиты Google, риск затирания при одновременной записи
- ❌ Один файл на 7000 строк — тяжело править без риска задеть чужой код
- ❌ Логика размазана между телефоном и сервером

---

## Вариант B — «Google-фронт + настоящая база»

```
Телефон/ПК ──> Apps Script (тонкий слой) ──> Supabase/PostgreSQL (данные)
```
Оставляем привычный деплой через Apps Script, но данные переносим в базу.
- ✅ Минимальный переезд, всё бесплатное остаётся
- ✅ Быстрые отчёты за год, надёжная работа команды
- ❌ Apps Script остаётся «бутылочным горлышком» по скорости и лимитам
- 👉 Промежуточный шаг, если жалко ломать текущий деплой

---

## Вариант C — «Обычный сайт + база» ⭐ мой выбор

```
Телефон/ПК ──> Статичный сайт (SPA, свой домен) ──> Supabase
               фронт разбит на модули       PostgreSQL + Auth + Storage + Realtime
```
Фронт — не один файл, а модули (`касса`, `аналитика`, `поставщики`, `компоненты`), собираются автоматически при деплое. Хостинг — бесплатный (Cloudflare Pages / Vercel / свой сервер в РФ). База — self-hosted Supabase (уже в планах, 152-ФЗ).
- ✅ Быстро, масштабируемо, свой домен, PWA «как приложение»
- ✅ Каждый модуль чинится отдельно — то, о чём просили (адаптивность, порядок в коде)
- ✅ Прямой путь к SaaS для других магазинов и к мультимагазину
- ❌ Нужен один раз настроить сборку и хостинг (недели работы)

---

## Вариант D — «Полностью свой бэкенд»

```
Телефон/ПК ──> Своё API (Node/Go) ──> PostgreSQL ──> своя инфраструктура
```
- ✅ Максимальная гибкость и контроль
- ❌ Дорого и сложно: нужен постоянный админ/разработчик, серверы, мониторинг
- 👉 Только для крупной сети магазинов, не сейчас и, возможно, никогда

---

## 🎯 Мой рекомендуемый путь

**Тремя шагами, каждый — самостоятельная ценность, без «переписать всё сразу»:**

1. **Разбить фронт на модули** (остаёмся на Google). Снаружи ничего не меняется, но код перестаёт быть «кашей» — правки становятся безопасными. Это можно начать хоть сейчас.
2. **Перенести деньги-расчёты на сервер** — прибыль, сверка кассы, долги считаются в одном месте. «2+2» одинаково на любом устройстве.
3. **Переехать с Таблиц на Supabase** (Вариант C) — **только когда упрёмся**: станет тормозить, появится второй магазин, или много сотрудников одновременно.

Ключевой принцип на всех этапах — **три независимых слоя**:
`Экран` (кнопки/окна) · `Логика` (правила бизнеса) · `Хранилище` (сегодня Таблицы, завтра Supabase). Слои не знают друг о друге → любой можно менять, не ломая остальные.

---

## Порог переезда (когда трогать)

Не раньше, чем сработает **хотя бы одно**:
- ⏳ Отчёты и списки начали заметно тормозить
- 🏪 Подключается второй магазин / сеть
- 👥 Много сотрудников пишут в приложение одновременно
- 📈 Операций больше ~30–50 тысяч в таблице

До этого Вариант A (Google) — правильный выбор. Не чиним то, что не сломано.
