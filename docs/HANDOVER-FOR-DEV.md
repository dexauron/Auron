## 0. TL;DR за 30 секунд

**Auron Finance** — веб-приложение (PWA) для финансового учёта розничного магазина.
Первый клиент — магазин **Way Market**. Заменяет бухгалтеру Excel и тетради: касса (Z-отчёты),
долги поставщикам, зарплата, аналитика, отчёт владельцу.

- **Фронтенд:** один большой HTML-файл `app/index.html` (SPA на чистом JS, без фреймворков), деплой на GitHub Pages.
- **Бэкенд:** self-hosted **Supabase** (PostgreSQL + Auth + PostgREST + Realtime + Storage) на российском сервере `201.51.6.170`.
- **Состояние:** рабочий прототип. Ядро (счета, транзакции, касса, долги) реализовано на ~11 таблицах. В документах `docs/` описана гораздо более амбициозная целевая архитектура (76 таблиц, двойная запись) — это план, не текущий код.

## 2. Продукт: что и для кого

Универсальная финансовая платформа: от личного бюджета до сети магазинов.
Модульная: **ядро** (счета, транзакции, категории, бюджеты, цели, аналитика) + **модули**
под тип бизнеса. **v1.0 = Модуль розницы** на примере Way Market.

**Позиционирование:** «штатный бухгалтер-аналитик за ₽890/мес». Ближайший аналог по духу — Zenmoney, но для бизнеса.

**Чего продукт НЕ делает принципиально:**
- ❌ не заменяет 1С (склад, ТСД, ценники)
- ❌ не POS-система (не принимает платежи)
- ❌ не CRM
- ❌ не бухгалтерское ПО для сдачи отчётности в налоговую

Тарифы: Личный ₽0 · ИП ₽299 · Бизнес ₽590 · Ритейл ₽890 · Сеть ₽690/магазин. Пакет ИИ — доп.

## 3. Как работает магазин — бизнес-логика (САМОЕ ВАЖНОЕ)

Чтобы понять приложение, надо понять, как живёт розничный магазин. Вот вся доменная логика.

### 3.1 Роли (не «кассир»!)
| Роль | Кто это | Что делает в приложении |
|------|---------|------------------------|
| **Владелец** | Хозяин магазина | Только смотрит: выручка, прибыль, долги, пульс |
| **Бухгалтер** | Ведёт учёт (часто удалённо) | Всё: касса, долги, зарплата, отчёты |
| **Администратор** | Старший в зале | Заказы поставщикам, запись выплат (без сумм кассы) |
| **Сотрудник зала** | Продавец | Только заказы и поставки, без денег |

⚠️ Роли «Кассир» НЕТ — Auron не кассовая программа. Кассир — это `employee`, который фигурирует в Z-отчёте, но не пользователь приложения.

### 3.2 Смена и Z-отчёт (ядро розницы)
Каждый день магазин работает сменами (День / Вечер / Ночь). В конце смены кассовый аппарат
печатает **Z-отчёт** — итог продаж по способам оплаты. Бухгалтер вносит его в приложение:

```
Z-отчёт (что показала касса):   Наличные + Карта + СБП = Z-итого
Фактически в кассе:              сколько реально наличных пересчитали
Выплаты с кассы:                 что из кассы отдали (инкассация, поставщику, Иман…)

РАСХОЖДЕНИЕ = (Факт наличные + Выплаты) − Z наличные
   отрицательное → 🔴 недостача (кассир недодал)
   ноль          → ✓ всё сошлось
   положительное → 🟡 излишек
```

Z-отчёт создаёт **доходные транзакции** (выручка по счетам) и **расходные** (выплаты).
Эти транзакции блокируются (`locked = true`) — их нельзя удалить, пока не отменить смену.

### 3.3 «Иман» — деньги владельца
Специфика этого магазина: владелец периодически берёт деньги из кассы на личные нужды.
Это отслеживается отдельной категорией (по умолчанию «Хозрасходы владельца»). В шаблонах Excel
и в ПУЛЬТЕ есть строка «Иман хозяйки за месяц». Для разработчика: это обычная расходная
операция с особой категорией, но её сумму показывают отдельным сигналом.

### 3.4 Долги поставщикам
Магазин берёт товар **в долг** у торговых представителей (ТП) и постепенно платит.
```
debt_entry type = 'debt'    → долг вырос (взяли товар)
debt_entry type = 'payment' → долг упал (заплатили) + создаётся расходная транзакция
debt_entry type = 'initial' → начальный долг на момент старта учёта

Остаток долга ТП = Σ(debt) − Σ(payment)
```
Просрочка = запланированная выплата, у которой дата прошла, а статус ещё «Запланировано».

### 3.5 Накопления и модель 25/75
Магазин откладывает деньги по статьям (Аренда, ЗП, Налоги). Финансовая модель:
**25% — норма прибыли, 75% — лимит на закуп** от выручки. Приложение показывает,
укладывается ли магазин в лимит закупа.

### 3.6 Зарплата
Табель по дням (вышел / полдня / выходной / больничный / отпуск) → в конце месяца
расчёт: дней × ставка − авансы = к выплате.

### 3.7 Финансовый пульс 🟢🟡🔴
Индикатор здоровья бизнеса в шапке. Взвешенная сумма: выручка vs средняя (30%),
долги vs лимит (30%), накопления vs план (20%), расхождения за неделю (20%).

## 4. Ключевые сценарии (из docs/02-FLOWS.md)
1. **Утро:** бухгалтер открывает ПУЛЬТ/Главную → видит выручку, сигналы, что не закрыто.
2. **Закрытие смены:** вносит Z-отчёт → расхождение считается само.
3. **Выплата поставщику:** отмечает оплату → долг пересчитывается, деньги уходят из кассы.
4. **Конец месяца:** расчёт зарплаты + закрытие месяца (после закрытия период не редактируется).
5. **Отчёт владельцу:** одна кнопка → WhatsApp/PDF.

## 5. Архитектура и стек

### 5.1 Общая картина
```
[Браузер / PWA]  app/index.html (SPA, ванильный JS)
      │  fetch → PostgREST
      ▼
[self-hosted Supabase на 201.51.6.170]
   ├─ PostgreSQL      — данные
   ├─ GoTrue (Auth)   — телефон + OTP, JWT
   ├─ PostgREST       — авто-REST поверх таблиц (порт через Kong :8000)
   ├─ Realtime        — WebSocket, живые обновления
   └─ Storage         — фото чеков (бакет receipts)
```
- **Kong** — API-шлюз, порт `8000`. **nginx** — отдаёт фронт (порт 80) на сервере.
- Данные в России (152-ФЗ) — сознательный выбор, был переезд с Supabase Cloud.

### 5.2 Слой данных — `app/js/api.js`
Своя мини-обёртка над PostgREST — конструктор запросов `_q('table').select().eq().get()`.
**supabase-js НЕ используется** для данных (только, возможно, для auth). Все суммы — в копейках.
Публичный объект `window.API` со всеми методами: `getOrgs`, `getAccounts`, `saveTransaction`,
`saveTransfer`, `getShifts`, `saveShift`, `getDebts`, `saveDebtEntry`, `getAnalytics` и т.д.

Баланс счёта обновляется через RPC `increment_account_balance(account_id, delta)` —
**простое инкрементирование, НЕ двойная запись** (см. §9 о расхождении с документами).

### 5.3 Авторизация — `app/js/auth.js`
Телефон → OTP-код → JWT. Плюс локальный **PIN (4 цифры)** и автоблокировка.
`AUTH.getToken()` даёт JWT для заголовка `Authorization` во всех запросах.

### 5.4 Изоляция данных — RLS
У каждой таблицы колонка `org_id`. Row-Level Security фильтрует по членству пользователя
в организации: `org_id IN (SELECT org_id FROM org_members WHERE user_id = auth.uid())`.
Чужой магазин прочитать нельзя даже прямым запросом к API.

### 5.5 Офлайн и реалтайм
- Service Worker `app/sw.js` — кэш (stale-while-revalidate), версия `auron-vNN` (бампать при каждом изменении фронта).
- `app/js/offline-queue.js` — очередь новых операций в localStorage, досыл при появлении сети, идемпотентность по `client_uuid`.
- Realtime WebSocket — живые обновления для нескольких устройств одного магазина.

## 6. Реальная модель данных (что фактически в БД)

Миграции: `infra/migrations/001_initial_schema.sql` … `004_fixes.sql`.
**Фактически реализовано 11 таблиц** (не 76 из docs/05 — см. §9):

| Таблица | Назначение | Ключевые поля |
|---------|-----------|---------------|
| `users` | Профиль (зеркало auth.users) | phone, name, preferences(JSONB) |
| `organizations` | Магазин | name, type, settings(JSONB) |
| `org_members` | Кто в каком магазине + роль | org_id, user_id, role |
| `accounts` | Счета (касса/карта/СБП/сейф) | balance_kopecks, icon, color |
| `categories` | Статьи доход/расход | type(income/expense/both) |
| `employees` | Сотрудники (кассиры для смен) | full_name, salary |
| `shifts` | Z-отчёты / смены | z_*_kopecks, fact_*, diff_kopecks, withdrawals_json |
| `transactions` | Операции | type(income/expense), amount_kopecks, account_id, shift_id, locked |
| `counterparties` | Поставщики / ТП | name, type, phone |
| `debt_entries` | Долги ТП | type(debt/payment/initial), amount_kopecks |
| `org_settings` | Настройки орг. (key-value) | key, value(JSONB) |

Заметки для разработчика:
- Суммы везде **bigint в копейках**. Деление на 100 — только при отображении.
- Перевод между счетами = **две** транзакции (расход + доход), см. `saveTransfer`.
- Мягкое удаление через `deleted_at` (корзина). Транзакции смены — `locked`.
- `client_uuid UNIQUE` на транзакциях — защита от дубля (двойное нажатие / повтор из офлайн-очереди).

## 7. Фронтенд — структура

```
app/
  index.html          ← вся SPA (~1800 строк): CSS + HTML-каркас + JS
  app_bundle.html     ← собранная версия (дубликат для оффлайн-раздачи)
  js/
    config.js         ← SUPABASE_URL + анон-ключ (НЕ секрет, но не коммитить лишний раз)
    api.js            ← слой данных (PostgREST)
    auth.js           ← авторизация (OTP + PIN)
    offline-queue.js  ← очередь офлайн-операций
    integrations.js   ← интеграции (заготовка)
    gapi.js           ← Google API (заготовка, legacy)
    supabase.min.js   ← клиент (для auth)
    chart.min.js      ← графики аналитики
  sw.js               ← Service Worker (PWA/кэш)
  manifest.json       ← PWA-манифест
  icons/              ← иконки приложения
```

Состояние приложения — глобальный объект `S` (orgs, accounts, categories, currentTab, np — данные нумпада и т.д.).
Навигация — функция `navigate(tab)` переключает вкладки. Данные грузятся в `loadTab(tab)`.

**Текущая навигация в коде** отличается от целевой (docs/03): в коде вкладки
Главная/Аналитика/Касса/Журнал/Настройки; по документам для Way Market должно быть
**Главная · Касса · Поставщики · Финансы · Ещё**. Это один из пунктов доработки.

## 14. Быстрые ответы на частые вопросы разработчика

- **Где логика расчёта расхождения кассы?** — `api.js`, функция `saveShift` (diff = факт+выплаты − Z).
- **Почему не supabase-js?** — сознательно, лёгкий свой слой на PostgREST (`_q()`), меньше зависимостей.
- **Почему один HTML-файл?** — v1 без сборки, деплой на Pages напрямую. Переход на Vite — когда `js/` > 15 файлов / 5000 строк (см. docs/05).
- **Где секреты?** — анон-ключ Supabase в `app/js/config.js` (публичный по дизайну, защита — через RLS). Ключи подписи APK — в GitHub Secrets.
- **Двойная запись есть?** — пока нет, в планах (docs/05). Сейчас баланс = инкремент.
