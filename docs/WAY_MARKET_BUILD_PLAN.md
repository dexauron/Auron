# Way Market — сборка единой системы

Статус: рабочий план реализации, 14.10.2026. Главный источник требований: [ТЗ Way Market](https://docs.google.com/document/d/14d7AtbjZycRv9k7Qr3iqWqIio1pMsZbv9IjnJKCloto/edit). Этот файл не заменяет ТЗ.

## Граница разработки

- Работа только в ветке `way-market/unified-system`. Оригиналы каталога Auron и Auron Finance, их публикации, базы и ключи не менять.
- `source-copies/catalog/` — неизменяемый снимок исходников для сравнения. `app/` унаследован от финансового приложения. Наличие этих папок не означает готовую интеграцию.
- Сначала локальные испытания на вымышленных данных. Рабочую 1С, бот, реальный магазин, платный хостинг и оплату внутри приложения не подключать.
- Каждая новая функция проходит проверку: права доступа, пустые и устаревшие данные, мобильный экран, повторная отправка, ошибки связи и восстановление после перезапуска.

## Целевые разделы

| Раздел | Данные и действия | Граница |
| --- | --- | --- |
| Открытый каталог покупателя | Поиск, категории, фото, карточки, розничные цены, наличие словами, дата обновления, популярное, избранное, список покупок | Публичные поля по разрешённому перечню, без внутренних финансовых данных |
| Заявка в WhatsApp | Список товаров и количества, выбран самовывоз или доставка, ориентировочная сумма; переход к отправке | Общение и подтверждение остаются в WhatsApp. Внутренний заказ и платёж автоматически не создаются |
| Рабочий каталог | Товары, штрихкоды, поставщики, остатки и действия по роли | Только авторизованные сотрудники; проверка права на уровне данных |
| Закупки | Заказ поставщику → резерв лимита → приёмка накладных → фактическое использование лимита | Заказ, накладная, долг и платёж — разные события |
| Деньги и сверка кассы | Подтверждённые выплаты и поступления, денежные счета, передача бухгалтеру, настраиваемая формула сверки | Платёж отдельно от заказа; идемпотентность и журнал изменений |
| Обмен и аналитика | Предпросмотр файлов 1С, проверка дублей, показатели и 33 KPI по мере реализации | Импорт не служит резервной копией 1С; определения KPI фиксируются отдельно |

## Первый проверяемый сквозной сценарий

1. Покупатель без входа открывает тестовый каталог с вымышленными товарами и фотографиями, ищет товар, видит розничную цену, `есть / мало / нет` и дату обновления. Неизвестный остаток так и обозначен.
2. Он составляет список; приложение показывает ориентировочную сумму и количество. При выборе «В магазине» список помогает отмечать покупки.
3. При выборе «Отправить в WhatsApp» покупатель указывает самовывоз или доставку. Приложение формирует читаемый текст и открывает WhatsApp; подтверждение, адрес, время, замены и оплату обсуждают там.
4. Ошибка открытия WhatsApp не стирает список. Приложение не утверждает, что сообщение отправлено, и не создаёт внутренний заказ/платёж по клику.
5. Доступ к публичному представлению не открывает закупочную цену, точные остатки, поставщиков, долги, продажи или персональные данные; это проверяется по реально отдаваемым данным, не только по интерфейсу.
6. При отсутствии достоверной выгрузки продаж «Часто покупают» не показывается как факт; допустима отдельно названная подборка магазина.

## Архитектурные решения к реализации

- Отдельная публичная модель товара, собранная по разрешённым полям. В клиентский пакет и публичный поиск не включать служебные данные. Старый каталог уже использует `buildPublicProducts()`, но новую границу надо проверить на всём пути публикации.
- Исходники каталога переносить в новый рабочий модуль, сохраняя `source-copies/` как эталон. Не смешивать публичный режим с авторизацией сотрудников через одно лишь скрытие кнопок.
- События финансов и закупок хранить раздельно, со стабильными ID, временем, автором и журналом исправлений. Повторные операции и импорт не должны дважды влиять на лимит и деньги.
- Формулы сверки кассы версионировать по магазину и периоду применения; результаты сохранять вместе с использованной версией. Редактор выражений не должен выполнять произвольный JavaScript.
- Для офлайн-режима сначала определить права и разрешённые действия. Конфликтующие изменения не применять молча.
- Визуальная цель: спокойный, читаемый мобильный интерфейс, высокая контрастность, понятные состояния пустоты/загрузки/ошибки; «премиум» подтверждается сценариями и проверкой на телефоне, а не только внешним видом.

## Не выдавать за готовность

Перенесённый код, экран с фиктивными товарами, описанный API или зелёный тест не означают готового фронтенда и бэкенда. Готовность каждого раздела отмечать отдельно: код → тестовые данные → проверки → интеграция → пилот. Реальный запуск требует отдельного решения владельца и проверки с данными магазина.
