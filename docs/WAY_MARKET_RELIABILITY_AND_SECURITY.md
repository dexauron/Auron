## 1. Архитектура и производительность

- Единый сервер с разделёнными внутренними модулями, общими ID и явными межмодульными командами. Сохраняем текущую основу Node.js/SQLite до измерений; смена базы не является обязательной целью.
- Индексированные запросы, выдача списков частями, фильтрация до передачи в браузер, загрузка только нужного раздела. Не скачивать всю историю на телефон.
- Импорт, фотографии/OCR, большие отчёты, архивирование и внешние ИИ-запросы выполняются в ограниченных фоновых заданиях; тяжёлая синхронная работа не блокирует приём HTTP-команд кассы.
- У задания ID, состояние, прогресс, ошибка, безопасный повтор и восстановление после перезапуска. Отмена после сохранённой части не выдаётся за полный откат; границы атомарности явные.
- Лимиты размера файла/запроса, длительности работы, памяти, очереди и числа параллельных заданий. Внешние вызовы имеют тайм-аут; повтор возможен только без двойного эффекта.
- Недоступность ИИ не мешает кассе и сохранённым данным. При отсутствии связи устройство не выдаёт локальное действие за подтверждённое сервером.

## 2. Сохранность и конкурентная работа

Команда, связанные изменения, проверенный автор и аудит сохраняются атомарно. Идемпотентный ключ повторной отправки связан с содержимым запроса. Ожидаемая версия защищает от потери чужого изменения. Сервер повторно проверяет права перед фиксацией, в том числе после длительной фоновой работы.

Статус «Сохранено» — только после подтверждения сервера. Неопределённый результат при разрыве связи требует проверки статуса команды по ID, а не создания новой операции. Черновик отделён от подтверждённой записи и защищён по аккаунту. Выход убирает сведения из интерфейса и доступной следующему пользователю памяти/хранилища. Публичный кэш не содержит финансовых данных.

История содержит исходную запись, версии, причину, автора и серверное время. Отчёт воспроизводится по снимку источников и версии формулы. Коррекция не скрывает первоначальное расхождение.

## 3. Модули безопасности

| Модуль | Требование |
|---|---|
| Аккаунты/права | Отказ по умолчанию; действие, магазин, объект, роль и версия проверяются сервером на каждом маршруте |
| Сеансы/устройства | Просмотр и отзыв активных сеансов; отключение пользователя/изменение прав завершает сеансы; явные сроки бездействия и жизни |
| Вход/восстановление | Медленное хеширование с уникальной солью, ограничение попыток/нагрузки, отсутствие паролей по умолчанию, безопасное восстановление и смена пароля |
| Критичные действия | Повторная проверка личности для управления правами, восстановления и иных опасных операций; обычные действия не перегружать подтверждениями |
| Журнал безопасности | Входы, изменения прав, чувствительные выгрузки, действия с копиями, отказы и ошибки; без паролей, токенов и API-ключей |
| Защита данных | HTTPS для сетевого доступа, ограниченные служебные права, секреты вне браузера/репозитория, защищённое хранение и отдельная защита ключей |
| Файлы/импорт | Проверка формата и структуры, размера, количества строк/вложений и распаковки; не исполнять макросы; безопасно отображать содержимое |
| ИИ | Минимальная разрешённая выборка, проверка роли до отправки, отсутствие секретов/лишних персональных данных; внешняя конфиденциальность проверяется до подключения |
| Сигналы/диагностика | Подозрительные входы, изменения полномочий, сбой защитных механизмов, нехватка места и неуспешное резервирование видны ответственному |

Дополнительно обязательны CSRF-защита команд, безопасное отображение текста, параметризованные SQL-запросы, строгая проверка входа, защита cookie (HttpOnly/SameSite, Secure при HTTPS), отсутствие доверия к роли/автору из браузера. Пароли/токены не помещать в URL, localStorage или sessionStorage.

Локальная база в текущем прототипе не объявляется зашифрованной. Защиту диска и секретов реализовать и проверить отдельно. Владелец приложения и администратор Windows — разные уровни полномочий: приложение не может гарантировать неизменность базы от администратора компьютера. Для независимого контроля нужна защищённая внешняя копия истории; цепочка хешей в том же файле сама по себе недостаточна.

## 4. Модули резервирования

| Модуль | Требование |
|---|---|
| Согласованный снимок | База, вложения, настройки, права/личности, аудит и необходимые версии схемы/формул с согласованной точкой восстановления |
| Автоматизация | Настраиваемое расписание и запуск перед обновлением/миграцией; состояние задания и обработка пропущенного запуска |
| Поколения | Несколько дат; свежая копия не уничтожает единственную исправную; очистка только после успешной новой копии и по политике |
| Отдельное хранение | Другой физический носитель; дополнительная отключённая/защищённая копия. Папка на том же SSD не защищает от его поломки |
| Шифрование | Шифрование резервного комплекта с контролем целостности; доступ только уполномоченным; ключ отдельно с проверяемым способом восстановления |
| Контроль | Последний успех, состав, размер, доступность носителя, ошибки, проверка целостности и уведомление владельцу |
| Проверка восстановления | Развёртывание в отдельную базу, сверка схемы, связей, контрольных итогов и доступности вложений |
| Аварийное восстановление | Выбор комплекта, предпросмотр, сохранение текущего состояния при возможности, контролируемое переключение и журнал результата |

Для SQLite использовать согласованный механизм резервирования, а не простое копирование работающего файла без учёта WAL. Целостность/контрольная сумма не доказывает подлинность источника копии. Вложения включаются по манифесту с проверкой наличия и целостности; незавершённый комплект не отмечается успешным.

Копии содержат чувствительные сведения и защищаются отдельно от обычных отчётов. Обычный бухгалтерский экспорт не содержит секретов и аккаунтов. Полная резервная копия может содержать проверочные хеши паролей, но не открытые пароли; обращаться с ней как с секретным материалом.

Расписание, сроки хранения, допустимая потеря последних данных (RPO), целевое время восстановления (RTO), носители, ключи и ответственные ещё не выбраны. Их надо явно настроить и измерить до пилота. Не выдавать технические значения по умолчанию за утверждённые владельцем.

## 5. Обновление и восстановление

1. Проверить совместимость схемы, достаточность места и свежую пригодную копию; предупредить пользователей о необходимом окне обслуживания.
2. Проверить обновление/миграцию на отдельной тестовой копии. Старый код может быть несовместим с новой схемой: откат одного исполняемого файла не всегда откат данных.
3. Применить контролируемую миграцию с журналом. Не выполнять неожиданную перезагрузку во время работы сотрудников.
4. При восстановлении сначала проверить отдельный экземпляр. Не перезаписывать активную базу из браузерной формы без отдельного защищённого сценария.
5. Аннулировать старые сеансы; не восстанавливать действующие токены как пригодные для входа. Уведомить владельца о результате и фактической точке восстановленных данных.
6. Разобрать операции после точки копии. Во избежание повторного движения денег сверить внешние документы, банковские сведения и незавершённые запросы; не воспроизводить вслепую уведомления/платежи из очереди.

Журнал восстановления содержит инициатора, выбранный комплект, время, результат и ошибки, без ключа расшифрования. Право скачивания/восстановления не следует автоматически из права просмотра отчёта.

## 6. Windows и эксплуатация

Автозапуск приложения после перезагрузки, ограниченная служебная учётная запись, отсутствие сна, проводное подключение, контроль диска/памяти/очередей, достаточное свободное место и план обновлений. ИБП для сервера и роутера желателен; его наличие не заменяет резервирование. Доступность приложения зависит от питания и сети выделенного компьютера.

Известная конфигурация владельца: i3-2120, 8 ГБ ОЗУ, SSD около 238 ГБ. Достаточность подтверждается нагрузочными измерениями на реалистичном числе товаров, документов и одновременных пользователей. Внешний доступ не означает публикацию RDP или базы в интернете; схему защищённого подключения выбираем и проверяем отдельно.

## 7. Обязательные приёмочные сценарии

| Проверка | Ожидаемый результат |
|---|---|
| Двойное нажатие, повтор после обрыва | Одна операция; запрос состояния по прежнему ID |
| Два редактора | Устаревшая версия отвергается; данные обоих не теряются молча |
| Перезапуск во время операции | Целая подтверждённая запись либо отсутствие частичной фиксации |
| Неверный/большой файл | Понятная ошибка, действующие данные не повреждены, касса отвечает |
| Диск заполнен/нет носителя копии | Нет ложного успеха; остановка опасной записи и уведомление |
| Недоступен ИИ | Основные рабочие функции доступны |
| Прямая ссылка/подмена ID/роль в запросе | Чужие данные и действия запрещены на сервере |
| Смена пользователя в общей вкладке/нескольких вкладках | Нет утечки карточек, поиска, диалогов, кэша и черновиков |
| Отзыв прав во время задания | Итоговая фиксация не использует устаревшее разрешение |
| Повреждённая/неполная/чужая копия | Восстановление отклоняется до переключения активных данных |
| Восстановление исправной копии | Связи, суммы, версии и вложения воспроизводимы; старые сеансы недействительны |
| Реальная эксплуатация | Проверены выбранные браузеры, Windows, печать, согласованная нагрузка и восстановление |

Все числовые цели скорости, нагрузки и восстановления фиксируются до приёмки. Сообщение об ошибке объясняет, что произошло, что известно о сохранении и какой следующий шаг безопасен. Интерфейс не показывает необоснованные «всё сохранено»/«база защищена».

## 8. Фактический статус

В кассовом прототипе есть локальные проверки ввода, целые копейки, версия записей, повторяемость сохранения, ограничение loopback, CSRF-проверка, архив кассовых данных и отдельное восстановление. Основа аккаунтов не включена в HTTP. Текущий JSON-архив кассы не включает аккаунты и не является полной копией целевой системы.

Автоматическое резервирование всего приложения, шифрование резервов, планировщик, защищённый сетевой доступ, независимый аудит и эксплуатационная диагностика пока не реализованы. Настоящие отключение питания, поломка диска и нагрузка на сервер владельца не проверены. Этот документ не объявляет такие проверки пройденными.
