## 1. Продукт и границы

Адаптивное веб-приложение/PWA для продуктового магазина в Грозном. Вход в личный аккаунт с телефона, планшета и компьютера через поддерживаемый современный браузер: iOS, Android, Windows, macOS, Linux. Совместимость подтверждать испытаниями; не обещать работу любого устаревшего браузера.

Общая база и документы располагаются на выделенном компьютере владельца с Windows Server. Один пользователь может работать с разных устройств, несколько пользователей — одновременно. Подтверждённые записи общие; черновики изолированы по пользователю и не считаются проведёнными операциями. Доступ в локальной сети и удалённый доступ проектируются отдельно. До готовности аутентификации и защиты данных сохраняется режим только 127.0.0.1.

Исходные приложения, ветки, публикации, базы и ключи не изменять. Разработка ведётся в изолированных ветках с последующим просмотром изменений для `way-market/unified-system`. Копии исходников не означают завершённую интеграцию. Рабочую 1С, ботов, платные услуги и реальную публикацию автоматически не подключать.

Публичный каталог не содержит внутренних финансовых данных. Онлайн-оплаты нет. Покупатель использует список в магазине либо отправляет в WhatsApp; подтверждение заказа, доставка, замены и расчёты остаются в переписке. Нажатие ссылки не означает отправку сообщения и не создаёт внутренний закупочный заказ или платёж.

## 2. Роли

Один аккаунт может совмещать обязанности; разрешения ограничиваются магазином, отделом, объектом и действием. Само название роли не даёт неограниченный доступ. Права проверяются сервером, в том числе при поиске, выгрузке, печати и передаче данных ИИ.

| Роль | Основная область | Ограничение |
|---|---|---|
| Покупатель | Публичный каталог, розничная цена, наличие в разрешённом представлении, избранное, список, WhatsApp | Покупка без обязательного аккаунта; покупательские аккаунты, если появятся, не получают внутреннего доступа |
| Сотрудник | Рабочий каталог, собственные задачи, разрешённые заявки/лимиты, свой табель и расчёты | Нет общего доступа к прибыли, чужим выплатам и кассам |
| Кассир | Полномочия сотрудника, сдача своей смены, свои уточнения | Открытие смены в программе не требуется; нельзя подтверждать приём денег за бухгалтера |
| Бухгалтер | Ввод за кассира, независимый пересчёт и приём, операции, проверка, отчёты и печать | Не подменяет чужое подтверждение; управление аккаунтами не предоставляется по умолчанию |
| Администратор магазина | Организация работы, задачи, сотрудники, справочники в разрешённых пределах | Финансы, прибыль, зарплаты и права не открываются автоматически |
| Торговый представитель | Свой поставщик, разрешённые документы, назначенные/выполненные выплаты, обращения | Нет чужих поставщиков и общего финансового журнала; заявление не проводит платёж |
| Владелец | Управление доступом, общая картина, контроль, настройки и разбор спорных действий | Изменения журналируются; нельзя скрыто переписывать историю |

Закупщик, заведующий отделом и кладовщик — настраиваемые профили полномочий сотрудника. Точный набор операций утверждается в матрице доступа до реализации соответствующего модуля. Покупатели не получают внутренних данных через изменение URL или роли в браузере.

## 4. Единая модель связей

У каждой сущности стабильный ID. Имена служат отображению, а не связыванию данных. Различаются аккаунт, сотрудник, сообщивший сведения, автор ввода, исполнитель, получатель и проверяющий. Хранятся время события и серверного внесения, магазин/область, источник, документы, версия и причина изменения.

| Сценарий | Последовательность и граница |
|---|---|
| Закупка | Потребность → заявка → резерв лимита → заказ → приёмка/накладная → обязательство → отдельная выплата. Поступление заменяет соответствующую часть резерва фактическим использованием; частичная поставка не закрывает весь резерв без основания |
| Недовоз | Приёмка → расхождение → претензия → ответ → исправленный документ/допоставка. Не принимать заказанное количество как фактически принятое |
| Переоценка | Закупочная цена → проверка маржи → предложение → согласование → применение → ценники. Черновик цены не меняет опубликованный каталог |
| Просрочка | Сигнал → физическая проверка → возврат/списание → товарный эффект и соответствующий учёт потери |
| Касса | Отчёты → фактические движения → расчёт → заявление кассира → пересчёт бухгалтера → разницы → проверка |
| Зарплата | Табель/основание → начисление или аванс → назначение → фактическая выдача → расчёты с сотрудником. Выдача не начисляет расход повторно |
| Подотчёт | Заявка → разрешение → выдача → документы → возврат остатка/долг → завершение проверки |
| Оборудование | Неисправность → задача → ремонт → расход. Испорченный товар списывается отдельным связанным событием |
| Закрытие периода | Полнота данных → сверки → начисления/расходы → показатели → зафиксированная версия. Позднее исправление создаёт новую версию отчёта |

Одна фактическая выдача может упоминаться в кассовой сдаче, ведомости и документе-основании, но уменьшает деньги один раз. Ссылки и проекции не создают новые операции. Временные назначения и резервы не выдаются за фактическое движение.

Сервер сохраняет связанную команду, бизнес-событие, аудит и исходящее уведомление атомарно. Доставка уведомлений повторяема; прочтение не означает согласие. Межмодульная связь не должна зависеть от открытой вкладки пользователя.

## 5. Расчёты и достаточность данных

Деньги — целые копейки с проверкой диапазона; дробное количество, себестоимость единицы и проценты — точные десятичные значения с явными правилами округления. Пустое значение не равно нулю. Общие суммы и их детализация не складываются повторно. Формулы и источники сохраняются с версией результата.

Валовая прибыль = выручка после возвратов − себестоимость проданного. Валовая маржа = валовая прибыль / выручка × 100%. Средняя наценка проданного = валовая прибыль / себестоимость проданного × 100%. Чистая прибыль = валовая прибыль + прочие доходы − относящиеся к периоду расходы и налоги. Нулевая база не даёт выдуманный процент. База НДС и полнота источников фиксируются отдельно.

Платёж поставщику не заменяет себестоимость проданного; поступление денег не всегда доход прибыли, изъятие владельцем не всегда расход прибыли. Точный эффект определяется видом события и учётной политикой. При недостающих данных показатель блокируется или явно предварительный. Количество чеков допускается агрегированным, если индивидуальные ID недоступны.

В общей выплате зарплаты не выдумывать получателей. Для персональной истории нужна детализация. Без партий и сроков нет достоверного контроля годности; без движений/проверенного снимка нет достоверного остатка. Перечень 33 KPI сверить с исходным файлом, не восстанавливать по догадке.

## 6. Простота интерфейса

Минималистичный интерфейс с принципами iOS, без сокращения полезного функционала. На компьютере — таблицы и боковая навигация; на телефоне — крупные элементы, адаптивные карточки и удобная последовательность ввода. Цвет не единственный носитель значения.

Касса: заполнение и отчёт на одном экране по Excel, виджеты наличных/эквайринга, настройки видимых полей, пояснения через «?». Плюс — зелёный текст со знаком +, минус — красный со знаком −, ноль нейтрален. Скрытое поле не должно терять ненулевое значение или незаметно менять расчёт.

Для каждой роли: главная, список, карточка, разрешённые создание/редактирование, история, задачи/уведомления, поиск и состояния загрузки/пустоты/ошибки/отказа. Все кнопки имеют проверяемое действие. Печать использует сохранённую версию, а не несохранённый экран. Массовые операции имеют предпросмотр и результат по записям.

## 7. Подтверждения и ошибки людей

Кассир может отправить сдачу до ответа бухгалтера на заявленное устное разрешение. Ответы: разрешал / не разрешал / требуется уточнение. Молчание не согласие. Значимое изменение суммы, назначения или документа требует нового подтверждения. Отзыв хранится отдельно и повторно открывает проверку, но не возвращает реальные деньги автоматически.

Исправления добавляют версии; нет тихого удаления проведённой истории. Ошибочный адресат заменяется новым запросом, чужое согласие не переносится. Нельзя независимо подтвердить собственную спорную выдачу. Отсутствие другого проверяющего показывается явно. Напоминания/замещение/эскалация помогают получить ответ, но не гарантируют действие человека.

## 8. Этапы и критерий готовности

1. Аккаунты, серверные права, разделение данных/черновиков, миграция личностей и аудит.
2. Полная касса, подтверждения, разбор ошибок, печать.
3. Сотрудники, табель, начисления/выплаты.
4. Каталог, закупки, приёмка, лимиты, склад по доступным источникам.
5. Поставщики/ТП, обязательства, банк и регулярные расходы.
6. Импорт, качество данных, прибыль/KPI, планирование.
7. Дополнительные операционные модули и ИИ в пределах прав.
8. Весь срок разработки: безопасность, резервирование, проверки отказов. Перед сетевым пилотом — эксплуатационные испытания Windows, восстановление и безопасный доступ.

Для каждой функции отдельно: требования → код → тестовые данные → проверки → интеграция → пилот. Готовность требует работающего сценария, серверной защиты, сохранности истории и восстановления, а не только макета/зелёного теста. Числовые цели времени ответа и восстановления определяются измерениями, фиксируются до пилота.
